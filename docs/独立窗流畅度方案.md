# 独立窗流畅度方案

> 目标：让 `standalone-py/` 那个窗口在**软件光栅（默认档）**下也能稳、省、跟手。
> 本文只谈独立窗——内嵌态跑在 DSH 的 Chromium 里，不吃分层窗口那套代价。
> 状态：方案清单，未实施。写于 2026-10-20，对应 v0.4.1 工作区。

---

## 0. 先把基线钉死

### 0.1 现在的渲染路径是什么

`ojingjing_py.py` 的 `_use_hw_gl()` 决定走哪条，默认是软件：

| 档位 | 环境变量 | 合成方式 |
|---|---|---|
| 软件（默认） | `QT_OPENGL=angle` + `QT_ANGLE_PLATFORM=warp` + `--single-process --disable-gpu --no-sandbox` | ANGLE/WARP 软件光栅，关 GPU 合成 |
| 硬件（实验） | `QT_OPENGL=angle` + `QT_ANGLE_PLATFORM=d3d11` + `--enable-gpu-rasterization --enable-zero-copy` | D3D11 + GPU 合成 |

窗口本身是 `FramelessWindowHint | WindowStaysOnTopHint | Tool` + `WA_TranslucentBackground` +
`WA_NoSystemBackground`，在 Windows 上就是**逐像素透明的分层窗口**。

**所有卡顿的总根**：这类窗口的重绘是一整块 `UpdateLayeredWindow`——不是「只重画变了的那块」，
而是「整窗位图重新算一遍 alpha 再交给合成器」。所以成本正比于 **窗口面积 × 重绘次数**，
两个乘数各有一个方案组。

### 0.2 已经做过的优化（别重复劳动）

这些已经在代码里，方案里不再提：

| 已做 | 位置 | 效果 |
|---|---|---|
| 内容未变就跳过 DOM 重建 | `app.js` `render()` 闸门 1 | 省掉 replaceChildren + 样式重算 |
| 软件模式关 `backdrop-filter` | `styles.css` §21 | 拿掉「每帧模糊背景」 |
| 软件模式停装饰动画 | `styles.css` §21 | 鲸鱼呼吸 / zzz / 星星 / 进度流光 |
| 工作环 `steps(48)` + 2.4s | `styles.css` §21 | 空闲 CPU 43% → 21% |
| 滚动去 `mask-image` 换 sticky 渐变 | `styles.css` §22 | 滚动容器不再每帧重新栅格化 |
| 滚轮期暂停动画 | `app.js` `bindScrollBoost` | 转圈/呼吸不跟滚动抢帧 |
| resize 攒批 40ms、变小延后 240ms | `ojingjing_py.py` `SizeReporter` | 消掉一串来回 resize |
| 帧率上限默认不解除 | `_high_fps()` | 避免 215% CPU |

### 0.3 还剩三个真瓶颈

1. **每帧整窗合成**——面板态窗口 444×604，其中真正有内容的只有 400×560，
   约 **20% 的像素是纯透明留白**，但它们照样参与每帧合成。
2. **定时器每跳全量建 DOM**——`app.js` 的闸门 1 是「先建完再比」：
   每跳都要跑一遍 `XJ.views.panel(s)`（几百个 createElement）+ 序列化整棵子树的 `outerHTML`，
   然后才发现「哦，一样」。三个定时器（1s / 2s / 2.6s）都在付这笔钱。
3. **硬件路径是死的**——GPU 合成下分层透明窗口拿不到那一帧，屏幕上看不见窗口
   （`PrintWindow` 抓出来内容却是好的）。所以现在只能吃软件光栅的亏。

### 0.4 改之前先量一遍

没有基线就没法证明「流畅了」。三个指标，**面板态和收起态要分开测**：

```powershell
# 1) 让外壳带调试端口起来
$env:QTWEBENGINE_REMOTE_DEBUGGING = "9223"
.venv\Scripts\python.exe ojingjing_py.py

# 2) 另一个终端量主线程帧间隔
node tools/dev/fps-probe.mjs 9223 5

# 3) 量进程 CPU 时间（10 秒内的增量，换算成单核百分比）
$p = Get-Process python; $a = $p.TotalProcessorTime.TotalMilliseconds
Start-Sleep 10
$b = (Get-Process python).TotalProcessorTime.TotalMilliseconds
"$([math]::Round(($b-$a)/100,1))% of one core"
```

> **陷阱：`fps-probe.mjs` 量的是 `requestAnimationFrame`，不是合成次数。**
> rAF 一直是 60 不代表窗口没在重绘——软件光栅下 rAF 跑满、合成掉帧是常态。
> 判断「省不省」看 **CPU 时间**，判断「卡不卡」看 **帧间隔 p95 / over_50ms**。

填这张表再动手：

| 场景 | 形态 | fps 中位数 | p95 ms | over_50ms | 单核 CPU |
|---|---|---|---|---|---|
| 空闲 | 收起（鲸鱼球） | | | | |
| 空闲 | 面板（首页） | | | | |
| 空闲 | 面板（有会话在跑） | | | | |
| 交互 | 面板滚动 | | | | |
| 交互 | 气泡进出 | | | | |

## 方案一 · render 前置签名闸门（ROADMAP F1）

**杠杆**：降主线程 CPU ｜ **量**：S（半天）｜ **风险**：无（有自校验兜底）

### 现状

`app.js` 的 `render()` 顺序是：先 `document.createDocumentFragment()` → 依次 append 各视图 →
把每个子节点的 `outerHTML` 拼成字符串 → 和 `lastStageHTML` 比 → 一样才 return。

问题在于「建」和「序列化」都发生在「比」之前。三个定时器每跳都要为一次注定被丢弃的重建付钱：

- `setInterval(tickClock, 1000)` — 相对时间
- `setInterval(tickExpiry, 2000)` — 审批超时
- `setInterval(() => XJ.mock.harness.tick(), 2600)` — 会话推进

而这三个定时器绝大多数跳变**根本不改任何可见内容**（时间只是从「3 分钟前」变成「4 分钟前」，
会话状态没动）。

### 做法

在 `render()` 最前面算一个 20~40 字符的状态签名，和 `lastSig` 相同就直接 `renderChrome(s); return;`：

```js
function stateSig(s) {
  const st = s.sessions.map((x) => x.id.slice(-4) + x.state + (x.unread || 0) + (x.pending ? x.pending.length : 0));
  return [
    s.ui.form, s.ui.panelScreen, s.ui.showOnboarding ? 1 : 0,
    s.connection, XJ.state.mainStatus(s).level,
    s.counts.pending, s.counts.unread,
    st.join(","),
    XJ.shot && XJ.shot.active ? 1 : 0,
  ].join("|");
}
```

签名要覆盖**所有影响 DOM 结构的字段**。漏一个就会出现「界面不更新」的鬼故事，
所以配一个开发期自校验：签名相同、但走完全量构建后发现 `html !== lastStageHTML` 时，
`console.warn("签名漏字段", sig)` 并把这次的签名差异打出来。**内嵌态和原型里都开着，跑一周没告警再关掉。**

注意 `tickClock` 改的是「3 分钟前」这类相对时间文本——它属于 DOM 内容，
如果被签名挡住就永远停在「3 分钟前」。两种处理：

- 把相对时间做成签名的一部分（把 `Math.floor(now - t)/60000` 的分钟数拼进去），代价是签名每秒变一次，
  但那种情况下本来就该重绘；
- 或者更省：让相对时间走 `renderChrome(s)` 里的一次 `textContent` 定点更新，不进结构重建。

**推荐第二种**——它顺带把「时间跳变触发整面板重建」这个隐藏问题一起解决了。

### 为什么有效

| | 现在 | 改后 |
|---|---|---|
| 定时器跳变（内容没变） | 建整棵 DOM + 序列化（约 1~3ms） | 算 30 个字符（约 0.02ms） |
| 每秒次数 | 1 + 0.5 + 0.38 ≈ 1.9 | 1.9，但每次便宜两个数量级 |

省下来的不是「帧率」，是**主线程余量**——交互时（hover、滚动、展开）不会被定时器抢走那 2ms。
这才是「手感」的来源。

### 验证

`fps-probe` 的 `over_50ms` 应该从面板态空闲的若干次降到 0；CPU 时间同步下降。
另外拿 `cdp-eval.mjs` 打点：在 `render()` 首尾各 `performance.mark` 一次，统计 100 次调用的中位数。

## 方案二 · 面板态装饰静默

**杠杆**：降重绘次数 ｜ **量**：S ｜ **风险**：低

### 现状

§21 在软件模式关了一批装饰，但**工作环还在转**（`steps(48)`，2.4s/圈 = 每秒 20 次合成），
`spinner` 也还在转。面板态窗口 444×604，每秒 20 次整窗合成 ≈ 每秒 530 万像素的 alpha 运算——
而用户此刻正在看列表、读审批，根本没在看那只环。

### 做法

面板态给 `<html>` 挂一个 `xj-panel`（`render()` 里已经有 `body.dataset.*` 那套，顺手加一个），
在 §21 后面追加一档：

```css
/* 面板态：装饰再降一档。工作环从 20 次/秒降到 2.7 次/秒，
   仍然看得出「在转」，但合成次数少 87%。 */
html.xj-sw.xj-panel .whale.st-focus .orbit-arm {
  animation-duration: 3s;
  animation-timing-function: steps(8, end);
}
html.xj-sw.xj-panel .spinner {
  animation-duration: 2s;
  animation-timing-function: steps(12, end);
}
```

更彻底的一步（可选，看第一批数据再定）：面板态把「正在干活」从**动画**换成**静态表达**——
工作环定格成一段静态弧 + 每 10 秒跳一次的小圆点，会话卡的状态点用颜色而不是转圈。
代价是视觉上没那么「活」，收益是面板开着时重绘次数趋近于零。

### 为什么有效

软件光栅下成本 = 面积 × 次数。面积不变，次数从 20/s 降到 2.7/s，**直接砍掉 87%**。
而且这 87% 是在用户正在读内容、最需要主线程空闲的时候省下来的。

### 风险

工作环 `steps(8)` + 3s/圈 = 每步 45°、间隔 375ms，能读出「在转」但会有轻微跳格感。
如果肉眼觉得顿，退回 `steps(16)`（5.6 次/秒）仍然比现在省 72%。

### 验证

同 0.4。重点看**面板态空闲 CPU**，应该从当前值掉到一半以下。

## 方案三 · 窗口面积贴合内容

**杠杆**：降单帧面积 ｜ **量**：S ｜ **风险**：低（可能裁到投影）

### 现状

`.panel` 是 `width: 400px; height: 560px`，但窗口实测是 **444×604**（见 §21 注释里的实测记录）。
差出来的 44px 是给投影/光晕留的透明边——**它们每帧都参与合成，却一个像素都看不见**。

`444 × 604 / (400 × 560) = 1.20`，也就是 **20% 的合成成本纯属浪费**。

### 做法

两种，二选一：

- **A（推荐）**：页面把投影画进 padding 内。现在投影是 `box-shadow` 溢出元素盒子，
  改成用 `::before` 伪元素 + 内缩的 `box-shadow`，让投影落在 `.panel` 的盒子里，
  然后上报尺寸时不再额外加边距。窗口直接变成 400×560。
- **B**：外壳侧对上报尺寸做 `-44` 的补偿（`SizeReporter.resize()` 里动手），
  但这是治标——投影会被裁掉一截，只在「投影本来就看不出来」时可用。

顺带检查 `MAX_W, MAX_H = 900, 900`：如果实际上报永远到不了 900，收窄到 640 也能防住
「某次异常上报把窗口撑成 900×900」导致的一帧巨额合成。

### 为什么有效

面积直接 -20%，成本线性 -20%。这是**唯一一条不需要改架构、不需要测、改完立刻生效**的方案。

### 验证

`ojingjing-py.log` 里每次 `resize` 都打印实际尺寸，改前改后对比即可。CPU 时间同步降约 20%。

## 方案四 · 鲸鱼位图化（静态层 / 动态层分离）

**杠杆**：降单帧成本 ｜ **量**：M ｜ **风险**：中

### 现状

鲸鱼是自绘 SVG（`whale.js`），有渐变、高光、多段 path。软件光栅下每次 `transform` 变化，
Chromium 都要**重新栅格化整个 SVG 子树**——哪怕变的只是眼睛的 `translate`。

### 做法

把鲸鱼拆成两层：

| 层 | 内容 | 更新方式 |
|---|---|---|
| 静态层 | 身体、渐变、高光、轮廓 | 预渲染成一张位图（`<canvas>` 或 data URL 的 `<img>`），只做 `transform` |
| 动态层 | 眼睛、嘴、泡泡、zzz、星星、光环 | 保持 SVG，独立元素 |

关键点：

- 位图要按 `devicePixelRatio` 生成 2 倍图，否则高 DPI 下糊；
- 用户自定义头像（设置里的「外观 · 头像」）走的是 `<img>` 那条路，本来就是位图，不受影响；
- 主题色/离线灰度变化时要重生成一次（离线态是 `filter: grayscale`，作用在容器上，不用重生成）。

### 为什么有效

位图变换在软件光栅下只需一次 alpha 混合，不用重新光栅化矢量。
鲸鱼是常驻元素、面积占比最大，这一刀通常能砍掉一半以上的单帧成本。

### 风险

- 头像/背景是用户可换的，缓存失效逻辑要写对（换图 → 重生成）；
- 位图 + 变换在高 DPI 下容易糊，必须 2x 图 + `image-rendering: auto`；
- 如果最终决定做方案五（双窗口），鲸鱼窗更小、这条的收益会打折——**两条别同时做**。

### 验证

`fps-probe` 的 `median_ms` 在鲸鱼动画期应该明显下降；配合 CDP 的
`Performance.getMetrics` 看 `LayoutDuration` / `RecalcStyleDuration` 是否变化（应该不变，
说明省的是光栅化不是布局）。

## 方案五 · 双窗口分层（鲸鱼窗 + 面板窗）

**杠杆**：降单帧面积 ｜ **量**：L ｜ **风险**：中高

### 现状

一个窗口承载全部形态。收起态是 96~108 的小球，面板态是 444×604，同一个窗口换尺寸。

### 做法

两个独立窗口，各自一个 `QWebEngineView`，加载同一份 `shell-res/`，靠 query 只渲染对应形态：

```
http://127.0.0.1:43121/xj/app.html?embed=1&host=py&surface=whale   （~160×160，可扩到气泡）
http://127.0.0.1:43121/xj/app.html?embed=1&host=py&surface=panel   （400×560）
```

页面侧 `app.js` 读 `surface`，只 append 对应的视图；面板窗在收起时 `hide()`，
鲸鱼窗在面板打开时 `hide()`（或保留，取决于要不要「鲸鱼从角落探头」的观感）。

### 为什么有效——以及为什么现在别做

面积从 444×604（26.8 万像素）降到 160×160（2.6 万像素），**-90%**。
听起来很香，但有个前提：**收起态得真的有连续动画，才值得为它开一个窗**。

而现在 §21 在软件模式下把鲸鱼呼吸停了，收起态基本是静止的——**没有每帧重绘，就没有可省的东西**。
所以这条的真实定位是：

> **它是 B1（正弦微浮动）/ B2（视线跟随鼠标）的配套设施，不是流畅度优化。**

如果哪天决定「鲸鱼要一直活着」（0.3~0.5px 微浮动 + 眼睛跟鼠标），
那 B1/B2 一上线就会把收起态从 0 重绘变成 60 帧/秒重绘，**这时双窗口是唯一能兜住的办法**；
反过来，不做 B1/B2 就先做双窗口，纯亏。

### 风险

| 项 | 代价 |
|---|---|
| 内存 | 两个 WebEngine view，同 profile 但渲染进程可能各一个，约 +80~150MB |
| Z 序 | 两个 `WindowStaysOnTopHint` 窗口之间谁压谁要显式管，托盘/全屏场景容易翻车 |
| 拖动 | 拖鲸鱼时两个窗口要同步移动 |
| 焦点 | 面板打开时焦点给面板窗，`Esc` 收起的判定要跨窗 |
| 截图 | 现在 `Ctrl+Shift+A` 要藏「自己」，得藏两个 |

### 验证

分别量两个窗口的 CPU；重点确认「拖动鲸鱼时面板窗没有跟着重绘」。

## 方案六 · 硬件渲染路径修复实验

**杠杆**：换合成器（一步到位）｜ **量**：M（实验）/ 不可预估（修复）｜ **风险**：高、结果不确定

### 现状

`ojingjing_py.py` 头部注释写得很清楚：硬件模式下**分层透明窗口拿不到 GPU 合成的那一帧，
屏幕上看不见窗口，但 `PrintWindow` 抓出来内容完好**。所以它被降级成 opt-in 的实验档。

这个现象说明：渲染是成功的，只是**输出没进到窗口该去的地方**。

### 可试的方向（按成功概率排序）

1. **去掉 layered window，改用 `setMask()` + 不透明背景**
   面板态其实不需要逐像素 alpha（见方案三），矩形窗口 + 圆角 mask 就能看。
   如果这条通了，面板态直接吃上 GPU 合成，收益最大。代价是圆角边缘有锯齿（Win11 可用
   `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` 让系统给抗锯齿圆角，Win10 没有）。

2. **只对鲸鱼球保留 layered，面板态走不透明窗口**
   是 1 的细化版，和方案五的组合方式不同但目标一致。

3. **Chromium 开关矩阵**：`--disable-features=DirectCompositionVideoSwapChain`、
   `--use-angle=d3d11`、`--disable-gpu-compositing`（注意：最后这个在软件模式下会让渲染进程
   8~9 秒后崩，别混用）、`--enable-features=UseSkiaRenderer`。一次只改一个，用
   `XJ_HW_GL=1` 起、看屏幕、看日志。

4. **`WA_NoSystemBackground` 是否是元凶**
   现在同时设了 `WA_TranslucentBackground` 和 `WA_NoSystemBackground`。
   后者告诉 Qt「别擦背景」，在 GPU 合成路径下可能让帧永远不提交。试去掉它。

### 判定标准

- 屏幕上**肉眼能看见**窗口（不是靠 `PrintWindow`）；
- `resize` 到面板尺寸不崩；
- `fps-probe` 的 `median_ms` 稳定在 16.7 附近且 `over_32ms` 为 0；
- CPU 比软件模式低（这是硬件路径唯一的意义）。

### 建议

**先花半天做开关矩阵，全部失败就明确放弃，别再往里投时间。**
这条的价值是「万一通了，方案一到五都不用做」；但按现在的证据，成功率不高。

## 方案七 · 页面不可见时冻结渲染

**杠杆**：降平均帧数 ｜ **量**：S ｜ **风险**：低

### 现状

托盘「隐藏」只是把窗口 `hide()` 了，但 `QWebEngineView` 仍在跑——页面里的定时器、
`rAF`、CSS 动画一个都没停。窗口隐藏期间的所有合成都是纯浪费（而且藏起来的窗口，
软件光栅下可能仍在做 `UpdateLayeredWindow`）。

### 做法

```python
# 隐藏
self.view.page().setLifecycleState(QWebEnginePage.LifecycleState.Frozen)
# 显示
self.view.page().setLifecycleState(QWebEnginePage.LifecycleState.Active)
```

`Frozen` 会暂停页面里的定时器、rAF 和网络轮询。恢复时要主动 `runJavaScript` 触发一次
`render()` + `loadSnapshot()`，否则会显示冻结前的旧状态。

Qt 6.4+ 才有 `setLifecycleState`；低版本退路是 `view.hide()` + 停掉 `Upstream` 的轮询。

### 为什么有效

托盘隐藏是**最常见的长驻状态**（用户关掉面板就把它扔角落）。这段时间的 CPU 直接归零，
笔记本上是实打实的续航。

### 风险

恢复时的「第一帧」会有一次全量渲染 + 数据拉取，可能闪一下。缓解：恢复时先显示上一帧缓存
（`grab()` 存一张），数据回来再换。

## 同类项目怎么做的（2026-10-20 检索）

先看别人在同一块地上盖了什么房子：

| 项目 | 栈 | 体积 | 实测 CPU | 窗口结构 | 关键手法 |
|---|---|---|---|---|---|
| [Wakuwaku](https://github.com/zhoupengjie/wakuwaku) | Rust + Tauri + **系统 WebView2** | 7–11 MB 单 exe | 空闲约 **1%** 单核 | 灵动岛 / 任务栏 / 壁纸层三种形态 | 只在帧变化时绘制；鼠标 hook 仅在光标靠近时开启；不打包 Chromium |
| [KKClaw](https://github.com/kk43994/kkclaw)（claw-desktop-pet） | Electron | 约 150 MB 安装包 | **2.8%** | **双窗**：精灵窗 200×220 + 歌词窗 400×100 | 球体只有 67px；`setIgnoreMouseEvents` 穿透；**Windows 上 `disableHardwareAcceleration` 换透明** |
| 哦鲸鲸（现在） | Python + PySide6 + QtWebEngine | 329 MB | 约 21%（工作态空闲） | **单窗**，96–900 随形态变 | 关动画、降频、滚动暂停 |

三条它们做了、我们没做的：

1. **窗口都很小**。最大的 KKClaw 精灵窗才 200×220。**没有一个项目用「444×604 的大透明窗」**。
2. **大面板不进透明窗**。KKClaw 干脆没有大面板；Wakuwaku 的灵动岛也是窄条。需要大面板时，它们用不透明窗口。
3. **Electron 在 Windows 上也放弃硬件加速**。KKClaw 的提交记录写着：
   `disableHardwareAcceleration 仅在 Windows 上启用，macOS 保留硬件加速以支持透明度`。

第 3 条最重要：**「逐像素透明 + GPU 合成」在 Windows 上是普遍难题，不是 Qt 独有的缺陷。**
所以别指望「修好硬件渲染」一招解决——方案六的成功率要按这条再往下调。

真正被验证过的解法是**结构上的**：窗口小、面板不透明。这就是方案八。

## 方案八 · 面板窗去透明化（结构性改造，推荐）

**杠杆**：换掉面板态的合成路径 ｜ **量**：M ｜ **风险**：中（双窗的协调问题）

### 洞察

现在一个窗口装所有形态，所以面板态（444×604）**必须**逐像素透明——但它根本不需要。

面板是不透明的深色底（软件模式下 `rgba(13, 19, 32, 0.94)`），真正需要 alpha 的只有**圆角那四个角**。
为了这四个角，整个面板每帧都在付 layered window 的代价。

### 做法

拆成两个窗口，**只有小的那个透明**：

| 窗口 | 尺寸 | 合成方式 | 理由 |
|---|---|---|---|
| 鲸鱼窗 | 96–200px | 逐像素透明（layered） | 面积小，成本天然低；圆轮廓需要 alpha |
| 面板窗 | 400×560 | **不透明矩形** + 系统圆角 | 面板本来就不透明，只有圆角需要处理 |

圆角两种实现，按系统版本选：

- **Win11**：`DwmSetWindowAttribute(hwnd, DWMWA_WINDOW_CORNER_PREFERENCE, DWMWCP_ROUND)`
  —— 系统给的抗锯齿圆角，零成本，和原生窗口一致。
- **Win10**：`setMask(QRegion(圆角矩形))` —— 硬裁剪，圆角半径 12–16px 时几乎看不出锯齿。

### 为什么这是「更好的方案」

| | 现在 | 方案八之后 |
|---|---|---|
| 面板态合成 | 软件光栅 + 整窗 alpha | DWM 合成 + 不透明 |
| 面板态需要降频吗 | 需要（方案二） | **不需要** |
| 面板滚动 | 每帧整窗重绘 | Chromium 最擅长的路径 |
| `backdrop-filter` | 必须关掉 | **可以用回来**（真玻璃效果） |
| 硬件渲染依赖 | 是（方案六） | 否 |

一句话：**面板态的所有妥协（方案二、三、四）都变成了可选项，而不是必需项。**

### 和方案五的区别

方案五是「两个窗口都透明」，所以它仍然要解决「小窗也贵」的问题，收益只来自面积。
方案八是「**只有小球透明**」，直接把面板态踢出 layered window 体系——**收益来自换路径，不是省面积**。
如果只做一个，做方案八。

### 代价

- 两个 `QWebEngineView`，内存约 +80~150MB（可接受，现在 329MB 的大头是内核）；
- 面板态失去「鲸鱼从面板角上探头」这种跨窗视觉（如果设计上有，得改成面板内的静态鲸鱼）；
- 拖动、Z 序、焦点、截图要同时管两个窗口；
- 面板窗的圆角在 Win10 上是硬裁剪。

### 验证

面板态滚动 `over_50ms` 归零、`p95 < 33ms`；面板态 CPU 明显低于现在。
如果面板窗走的是 DWM 合成，`backdrop-filter` 重新打开后 CPU 不应显著上升——这是判断「真的换路径了」的标志。

## 方案九 · 换壳到 Tauri + 系统 WebView2（彻底，但工作量大）

**杠杆**：体积与渲染路径同时换 ｜ **量**：L ｜ **风险**：中（有明确的失败判定）

### 依据

Wakuwaku 用同一条栈做到 **7–11MB 单 exe / 空闲 1% CPU**。差别的来源不是它代码写得多好，
而是**它不打包 Chromium**——直接用系统 WebView2（Win10 1803+ / Win11 自带）。

我们现在 329MB 里 **194MB 是 QtWebEngine 内核**，占 59%。

### 渐进迁移路径（关键，别一次重写）

`ojingjing_py.py` 有 2926 行，一次翻译成 Rust 是不现实的。可行的做法是**先只换窗口层**：

1. 用 Tauri 写一个最小窗口，加载**现有的** `http://127.0.0.1:43121/xj/app.html?embed=1&host=py`；
2. Python 外壳照常跑，继续提供 `LocalServer` + `/xj/*` 反向代理 + QWebChannel 桥；
3. 只把窗口相关的能力（置顶、透明、拖动、热键、托盘）换到 Tauri 侧；
4. 量四个数：**透明是否正常、fps、CPU、体积**；
5. 通过 → 再逐步把截图、陪伴计时、设置面板迁过去；不通过 → 明确放弃，写进 README。

**这个验证只要半天，且不改任何现有代码**——新建一个 `standalone-tauri/` 目录，现有 `standalone-py/` 一行不动。
这是全文档里投入产出比最高的一步。

### 迭代速度不会倒退

这是当初删掉 WPF 版本时最担心的点，但对 Tauri 不成立：

- 页面在 `shell-res/` 里是**外部资源**，改 HTML/CSS/JS 只需覆盖文件 + reload，**不用 `cargo build`**；
- 只有 Rust 侧的窗口逻辑改动才要编译，而那部分很稳定，写完基本不动。

### 代价与前置

| 项 | 说明 |
|---|---|
| Rust 工具链 | MSVC，首次构建慢；CI 要装 |
| WebView2 Runtime | Win11 自带；Win10 需检测并引导安装（多数机器随 Edge 已有） |
| 透明性能 | Tauri 源码里对 Windows 的 transparent 有明确警告：resize / drag 时性能差 |
| 功能重写 | 热键、托盘、截图、单实例、设置、陪伴计时都要用 Rust 插件重做一遍 |

### 顺带纠正一个历史判断

README 说 WPF + `WebView2CompositionControl` 那版被删是因为「每次改动都要 `dotnet publish`」。
但页面是外部资源，**改页面根本不需要重编译**，只有改 C# 窗口逻辑才需要。
所以当初删它的理由可能被高估了——`WebView2CompositionControl` 走的正是 DirectComposition，
理论上是这条路上最正的解。如果将来要重做窗口层，WPF 和 Tauri 都值得重新评估一次。

## 体积 × 流畅度：到底能不能兼顾

### 先破除一个误解

「体积小」和「动画流畅」在 Windows 上**不是一对矛盾**。

329MB 不是「流畅的代价」，是「重复打包了一份 Chromium」的代价。现在装的 QtWebEngine 194MB，
和系统里已经躺着的 Edge WebView2 是**同一个东西的两个副本**——同样的 Chromium、同样的 GPU 能力。

所以「改用系统 WebView2」这件事：

| | 变化 |
|---|---|
| 体积 | 194MB → 0（系统已有） |
| GPU 能力 | **完全不变**（还是 Chromium） |

Tauri 的体积优势**不来自更轻的引擎**，来自「不重复打包」。
它并没有拿流畅度换体积——这是它最容易被误解的地方。

### 但换壳不会自动变流畅

这点必须说清楚，否则会失望。透明窗口的物理规律不因框架而变：**仍然是「面积 × 次数」**。

Wakuwaku 的 1% CPU 是三条一起做到的，缺一不可：

| 做法 | 解决什么 | 我们现在 |
|---|---|---|
| 用系统 WebView2 | 体积 194MB → 0 | 没做 |
| 窗口小（灵动岛是窄条，不是 444×604） | 合成面积 | 444×604 |
| 只在帧变化时绘制 | 合成次数 | 定时器每跳全量建 DOM |

所以「兼顾」的方案必须是**组合**，不是单选。只换壳不做双窗，面板态照样吃整窗 alpha；
只做双窗不换壳，体积还是 329MB。

### 四个候选的三维账

| 方案 | 体积 | 面板态流畅 | 小球态流畅 | 成本 | 备注 |
|---|---|---|---|---|---|
| 现状（Qt 单窗） | 329MB | 差（CPU 光栅） | 中（已静止） | 0 | — |
| 留在 Qt + 方案八 | 329MB | **好**（不透明窗） | 好 | M | 体积不动，只解决流畅 |
| **Tauri + 系统 WebView2 + 双窗** | **约 12MB** | **好**（GPU 合成） | **好** | L | 三项全优，代价是 Rust |
| WPF + `WebView2CompositionControl` | 约 26MB | 好（DirectComposition） | 好 | L | 项目试过，被"要重编译"劝退 |

后两行的体积都是**不含 Chromium** 的，因为用的是系统 WebView2。

> **必须用 Evergreen（共享运行时），不能用 Fixed Version 分发。**
> 后者会把约 180MB 的运行时打进包，体积优势当场消失。

### 推荐：Tauri + 双窗，但分两步走

**第一步只换窗口层**（半天，不改现有代码）：

Tauri 壳加载现有的 `http://127.0.0.1:43121/xj/app.html`，Python 后端继续跑。
量四个数，其中**「透明窗口在 GPU 下能不能正常显示」是唯一的生死项**——Qt 正是死在这一条。

Tauri/WebView2 默认是**开**硬件加速的（`hardwareAcceleration: false` 是排障开关，
用来解决 NVIDIA 白屏），说明它的透明路径和 Qt 的 layered window 不是同一条。
这是这条路值得试的理由。

**第二步做双窗**：小球透明 + 面板不透明。这一步和用哪个框架无关，
是 Windows 透明窗口的通用解法（同类项目无一例外）。

### 如果想保留 Python

`pywebview` 的 EdgeChromium 后端也是 WebView2，体积约 **30MB**（Python 运行时 + 系统 WebView2），
比 329MB 小一个数量级，且开发体验不变。

但 README 里记着它 import 阶段就崩（`System.Windows.Forms.IFileDialog` 不公开）——
**那是 WinForms 后端的问题**，EdgeChromium 后端值得单独试一次。
能力边界（逐像素透明、置顶、点击穿透、多窗口）要先验证，别一头扎进去。

### 一条要提前知道的代价

Tauri 源码里对 Windows 的 `transparent` 有明确注释：**resize / drag 时性能差**。
所以即使走这条路，「窗口尺寸跳变」这件事仍要按方案三的思路处理（内容动画代替窗口动画）。
换壳不是免罪金牌。

## 不建议做的

| 想法 | 为什么不行 |
|---|---|
| `QT_OPENGL=software`（swiftshader） | 本机实测窗口一放大渲染进程就退出，现象是「点开面板窗口就消失」 |
| `highFps` 默认开 | 软件光栅下 rAF 60→300、CPU 0.5 核→2.2 核，纯亏 |
| 全窗 `setMask()` 做圆形鲸鱼 | 硬裁剪无抗锯齿，边缘一圈锯齿，比现在的逐像素 alpha 丑得多 |
| 给所有动画元素加 `will-change` | 合成层数量爆炸，软件光栅下每层都要独立位图，反而更慢 |
| `mask-image` 做滚动淡出 | 已踩过：Chromium 会把它当「每帧重新栅格化」的层 |
| `--disable-gpu-compositing` | 渲染子进程 8~9 秒后崩（`0x80000003`），连 about:blank 都一样 |
| 缩短 `_shrink_timer` 让收起更快 | 收起动画会被窗口裁掉一截；现在 240ms 是实测出来的 |

## 推荐顺序

先做一次「半天就能出结论」的岔路判定，再决定后面走哪条路。

```
第零步（半天，不改现有代码）
  方案九的最小验证：新建 standalone-tauri/，一个 Tauri 壳加载现有的 43121 页面
      │
      ├─ 透明正常、fps 稳、CPU 明显低  →  走分支 B
      └─ 不行 / 不想换栈            →  走分支 A
```

**分支 A：留在 Qt（稳，改动可控）**

```
第一批（一天内，零/低风险）
  方案一 render 前置签名  →  方案三 窗口面积贴合  →  方案二 面板态静默  →  方案七 隐藏冻结
       ↓  按 0.4 的表复测
第二批（结构性，收益最大）
  方案八 面板窗去透明化     ← 做完这条，方案二/三/四 的妥协大多可以撤回
第三批（看数据）
  方案四 鲸鱼位图化        ← 只有当「鲸鱼动画期」仍是 p95 大头时才做
可选支线
  方案六 硬件路径实验      ← 按同类项目的证据，成功率进一步下调，限时半天
```

**分支 B：迁到 Tauri**

```
页面侧的改动照样有用（方案一 / 二 / 三 与外壳无关），先做掉
方案五 / 六 / 八 全部作废 —— 换了合成器就没有 layered window 这个问题了
把力气放在「Rust 侧能力补齐」：热键、托盘、截图、单实例、陪伴计时
```

判断依据很简单：**第一批做完，面板态空闲 CPU 应该掉到原来的一半以下、`over_50ms` 归零。**
如果没到，说明瓶颈不在「次数」而在「单帧成本」，那就直接跳到方案四或方案八；
如果到了但滚动手感仍差，再单独查滚动路径（`bindSmoothScroll` 的 rAF 逼近策略）。

## 一句话总结

前面七个方案都是**在错误的架构上做优化**——为了「面板的四个圆角」，
让整个 444×604 的窗口每帧都走 layered window 的 CPU 光栅。

同类项目（Wakuwaku 1%、KKClaw 2.8%）的共识是两条：**窗口要小**、**大面板不进透明窗**。
所以真正该做的是**方案八**（结构性）或**方案九**（换壳）；
方案一到七只是「在你决定改结构之前，先把能捡的捡了」。

**关于「体积和流畅能不能兼顾」**：能，但要认清它们不是同一根杠杆。

- **体积**由「打不打包 Chromium」决定 → 只有换到系统 WebView2（Tauri / WPF）能解决；
- **流畅**由「透明窗口多大、多久重绘一次」决定 → 只有双窗 + 降频能解决；
- 两者**互不影响**，所以可以都要：**Tauri + 系统 WebView2 + 双窗**，约 12MB 且面板态走 GPU。

反过来说，只换壳不做双窗，面板照样卡；只做双窗不换壳，体积照样 329MB。
真正的取舍只有一个：**愿不愿意为了 12MB 接受 Rust 工具链**。
